- Allison (demo/support email assistant on support@useagentcloud.com via AgentMail): conversations live in allison_threads/allison_messages, written only server-side (demo-request route, AgentMail webhook, `/api/public/hooks/allison-replies` cron every 5 min); what she may say lives only in src/lib/allison/knowledge.ts. Why: one source of product facts and no duplicate or forged replies.
- Demo forms send an AgentMail support-inbox notice, tracked as an internal conversation message for scheduled retry; Allison uses the AI Gateway SDK Responses contract. Why: support sees the submitted form independently of AI replies, without exposing internal notices to the assistant.
- Demo acknowledgments use the shared branded email sender and registry, queued before Allison scheduling; per-event Reply-To passes unchanged through the email queue. Why: confirmations retain the verified noreply sender while replies reach the support conversation.
- Allison escalation intake stays non-escalated until a customer answers follow-up questions and a complete structured report is available; owner delivery uses an internal message marker before closing automation. Why: humans receive actionable context and failed email sends remain retryable without claiming a handoff.

- Payment calls use the shared gateway-backed stripe.server.ts and embedded checkout; payment_subscriptions/payment_events isolate test and live state, and only live payment events update workspace entitlements. Why: test purchases cannot change real customer access or reuse legacy Stripe customer IDs.
- Workspace write access is decided only by computeAccess in src/lib/billing/access.ts (via getAccessFor, using the build's payment environment); checkout/portal reject any environment other than the build's. Why: test purchases unlock only the preview and can't grant live access.
- The Command Center server-to-server Admin API lives entirely in src/routes/api/public/admin.ts, gated by a bearer token against AGENT_CLOUD_ADMIN_KEY with a constant-time compare; ticket statuses are mapped at the boundary (Command Center in_progress ↔ database pending) and delete_user archives (terminate profile, strip roles, ban auth) rather than hard-deleting. Why: the prefix bypasses site auth so the handler is the only gate, and hard-deleting a user cascades to the profile and orphans the agency's production history.
- Self-serve signup lives on /start: visitors pick an agent or agency path first, create their account next, and every step saves to onboarding_sessions (path-aware welcome/resume/live emails sent once per user); the workspace is created at the build step via initSoloWorkspace then applyBuilderSetup, before checkout. /signup redirects there; SetupRedirect sends owners with onboarding_completed_at null to /setup; setup rules live in src/lib/onboarding/setup.ts. Why: one signup path, progress survives devices, and emails match the chosen path.

- Marketing pages (src/lib/hosts.ts isMarketingPath) live on useagentcloud.com; every other page, including login/signup/invites, lives on app.useagentcloud.com via a client-side host redirect in __root. Why: sessions are per-host, so account flows must share the product's host.
